# ShopLite 测试计划

| 项目 | 内容 |
|---|---|
| 被测系统 | ShopLite 简易电商平台 v1.0 |
| 文档版本 | v1.0 |
| 编写日期 | 2026-10-29 |
| 适用课程 | 软件测试 / 电子商务平台测试 |
| 测试类型 | 功能测试、UI 一致性测试、自动化测试、安全测试 |

## 1. 项目背景与目标

ShopLite 是一个课程用简易电商平台，提供商品浏览、购物车、结算支付和用户中心。本计划用于指导对该系统的测试设计、执行与结果归档，并为小组作业提供可追溯的测试过程证据。

测试目标：

1. 功能用例覆盖商品、购物车、结算、用户四大模块的全部需求，自动化用例通过率 100%。
2. 核心购买旅程（登录 → 筛选 → 加购 → 结算 → 支付 → 查看订单）100% 自动化执行。
3. UI 一致性覆盖主要页面的公共元素、标题规范与主按钮样式，人工检查 + 自动化断言双重验证。
4. 安全测试覆盖登录表单、支付流程与会话管理，输出按高/中/低分级、带证据与修复建议的报告。

## 2. 测试范围

### 2.1 范围内

- 商品列表、关键字搜索、分类筛选、价格区间筛选、排序、分页、商品详情
- 购物车加购、数量修改、删除、清空、库存上限、游客购物车与登录合并
- 结算表单校验、订单创建、模拟支付成功/失败/取消、订单历史与详情
- 用户注册、登录、退出、个人资料
- 页面 UI 一致性
- 登录表单与支付流程的安全测试

### 2.2 范围外

- 真实第三方支付网关对接与真实资金交易
- 性能测试、压力测试、并发测试
- 多浏览器/多设备兼容性矩阵（以 Edge 无头模式为主，手工抽查响应式布局）
- 管理员后台、物流、优惠券、邮件通知
- 生产环境安全渗透（仅限本地课程环境）

## 3. 测试策略

### 3.1 功能测试

- 采用等价类划分、边界值分析、场景法设计用例。
- 每个需求同时覆盖正常流、异常流与边界值，例如：数量为 0、超过库存、价格区间上下限、空购物车结算、支付失败重试等。
- 使用 pytest 参数化与独立测试数据库，保证用例可重复执行、互不影响。
- 每条用例记录：编号、模块、前置条件、步骤、预期结果、优先级、自动化映射。

### 3.2 UI 一致性测试

先手工检查，再用 Selenium 对可断言项自动化：

| 检查项 | 检查方式 |
|---|---|
| 每页均有统一头部、页脚、主导航 | 自动化断言 |
| 页面标题格式为「页面名 · ShopLite」 | 自动化断言 |
| 主按钮颜色、圆角、内边距一致 | 自动读取 computed style 比对 |
| 字体层级、字号、行高 | 人工检查 |
| 表单错误提示统一为页面顶部 flash 样式 | 人工检查 + 自动化断言 |
| 空状态（空购物车、无订单、无搜索结果）样式一致 | 人工检查 |
| 375 / 768 / 1440 宽度下布局正常 | 人工截图检查 |
| 页脚版权与品牌信息一致 | 自动化断言 |

### 3.3 自动化测试

- 采用 Selenium 4 + pytest + Page Object Model，页面元素使用 `data-testid` 定位。
- 全部使用显式等待（WebDriverWait），禁止 `time.sleep`。
- 每个用例前重建数据库、启动全新浏览器，保证独立性。
- 覆盖核心链路与关键异常流：游客购物车合并、结算校验、支付失败、缺货商品。
- 输出 pytest-html 报告，失败时保留截图（可按需扩展）。

### 3.4 安全测试

采用黑盒方法，覆盖 OWASP 常见风险类别：

- 注入：登录表单 SQL 注入
- XSS：搜索反射型、个人简介存储型
- 业务逻辑：结算金额客户端篡改
- 认证与会话：暴力破解、用户枚举、退出后会话失效、Cookie 标志
- 数据保护：支付卡号、用户密码是否明文存储
- CSRF：写接口是否缺少 Token

所有检查由 `tests/security/security_scan.py` 自动执行，证据（请求、页面响应、数据库记录）写入安全测试报告。

## 7. 进度与分工

按 4 周、4~5 人小组编排；人数不足时可合并角色，但每项产出必须有负责人。

| 阶段 | 时间 | 产出 |
|---|---|---|
| 需求与骨架 | 第 1 周 | 可运行的 ShopLite、种子数据、手动走通下单 |
| 测试设计 | 第 2 周 | 测试计划、测试用例、追溯矩阵 |
| 功能测试与自动化 | 第 3 周 | 功能用例执行结果、Selenium 脚本、缺陷记录 |
| UI/安全与收尾 | 第 4 周 | UI 一致性结论、安全报告、报告整合、答辩演示 |

参考分工：

| 角色 | 职责 | 可展示产出 |
|---|---|---|
| A 后端 | 数据模型、购物车/订单逻辑、模拟支付 | 被测系统后端代码 |
| B 前端 | 页面与统一样式 | 页面、UI 检查单 |
| C 功能测试 | 测试计划、用例、执行、缺陷记录 | 用例表、缺陷台账 |
| D 自动化 | Selenium 框架、脚本、报告 | 自动化工程与 HTML 报告 |
| E 安全 | 安全用例、扫描、报告 | 安全测试报告 |

## 8. 风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| Selenium 脚本不稳定（flaky） | 自动化结果不可信 | 强制显式等待；用例独立数据库与浏览器；失败保留截图 |
| 浏览器/驱动环境差异 | UI 测试无法执行 | 固定 Edge headless；Selenium Manager 自动管理驱动；README 注明环境要求 |
| 测试数据相互污染 | 断言随机失败 | 自动化使用临时数据库，每个用例前后重置 |
| 安全漏洞影响演示 | 演示环境被误用 | 仅本地运行；README 与报告显著标注；模拟支付不产生真实交易 |
| 需求理解偏差 | 用例遗漏 | 需求追溯矩阵检查覆盖度，评审时逐条核对 |
| 时间不足 | 交付物不完整 | 优先保证 P0 用例与核心链路自动化，P2 用例可手工覆盖 |

## 9. 准入与准出标准

准入：

- 被测系统可正常启动，种子数据加载成功
- 测试环境依赖安装完成，Edge 可正常启动
- 测试计划与用例评审通过

准出：

- P0、P1 功能用例全部通过，无未关闭的高优先级缺陷
- 核心购买链路自动化脚本稳定通过（连续执行 3 次结果一致）
- UI 一致性检查单全部完成，不一致项有结论
- 安全测试 12 项检查全部执行，发现项均有等级、证据与修复建议
- 测试报告与安全报告归档到 `reports/` 与 `docs/`
